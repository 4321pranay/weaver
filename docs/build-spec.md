# Build Output Spec

What a weaver build records besides the map: the run id, the releases it
built, each service's edge history, the code versions kept, and the internal
libraries it indexes. Spring services are also captured by spring-probe
([spring-probe-spec.md](spring-probe-spec.md)); its open keys become `config`
questions.

---

## 1. Run id

Every build of a domain has a **run id**, derived from what it built:

    run-<first 12 hex of sha1(sorted lines "<gitUrl>@<commit>" of every service built)>

The same sources always give the same run id; a service at another commit gives
a new one. A service that isn't a git checkout counts as `@nogit`.

The run id is written into every output of the build:

| Output | Where |
|---|---|
| `edges.yaml`, `edges.history/<svc>/<ver>.yaml` | `run:` |
| `releases.yaml` | `run:` |
| `questions.yaml` | `runs[].id`, and each question's `firstRun` / `lastRun` |
| `kb.db` | column `run` of table `domains` |
| `zoekt/` | repository metadata `run` (query with `meta.run:`) |
| `graph.html` | the page subtitle |

So any file, row or search hit can be traced back to the exact sources that
produced it, and every problem a build raised can be followed through
`questions.yaml`.

## 2. Releases: `releases.yaml`

`releases.yaml` records, for each service, the release this build analysed and
the releases before it.

```yaml
# knowledge/<domain>/releases.yaml (generated by weaver build; do not edit)
version: weaver/releases/v1.0
run: run-a82557c687e1
builtAt: 2026-10-24T10:12:00Z
services:
  - serviceName: checkout
    releases:                             # newest first
      - version: 1.4.0
        commitHash: a1b2c3d4e5f6
        builtAt: 2026-10-24T10:12:00Z
        edges: 1.4.0                      # this release changed checkout's edges
      - version: 1.3.2
        commitHash: 9f8e7d6c5b4a
        builtAt: 2026-10-10T08:01:00Z
        edges: 1.3.0                      # unchanged since 1.3.0: same snapshot
        gitUrl: https://git.example.com/shop/checkout   # first release
  - serviceName: payment
    releases:
      - {version: 2.0.1, commitHash: 0a1b2c3d4e5f, builtAt: 2026-10-24T10:12:00Z, edges: 2.0.0,
         gitUrl: https://git.example.com/shop/payment}
```

| Field | Meaning |
|---|---|
| `releases[0]` | The release this build used, which is the one `edges.yaml` describes |
| `version` | The release version, from the build file (§2.1); it identifies the release |
| `commitHash` | The full commit SHA built for that version: the latest one, when a version is built at several commits |
| `edges` | The version of the edge snapshot that describes this release (§3) |
| `gitUrl` | The repo the release was built from. Written only on the first release and on a release whose repo differs from the one before it (the repo moved); every other release has the repo of the release before it. The branch isn't recorded: `commitHash` pins the code |

**Rules:**

- **New release:** one is added only when a service's `version` changes. A new
  commit with the same version updates that release's `commitHash` and
  `builtAt`; rebuilding the same commit leaves the history untouched.
- **Removed services:** a service removed from `sources.yaml` is left out of
  the next generation's `releases.yaml` and map. Its snapshots, Zoekt branches
  and kb.db documents stay in the shared stores, because older generations
  still list them, so an RCA about a retired service can still be checked.
- **Growth:** nothing is ever deleted, by choice. The stores grow with what
  changes (§4 gives the estimate), and every generation adds only
  its own small files.
- **Same generation:** the file is written into the same generation as
  `edges.yaml` (weaver-architecture §2), so it always describes the
  `edges.yaml` next to it.
- **Failed fetch:** if a service's fetch fails and the previous clone is used,
  its `releases[0]` stays as it was.

### 2.1 Release version

`version` comes from the service's build file, read in the build itself:
Maven `<version>` (properties resolved), Gradle `version`, or, for Go and
anything else, `version.json` at the service's root (`{"version": "1.4.0"}`).
Git tags are not used: a branch has one version until its build file says
otherwise, so two releases can never share a name.

A service with none of these raises a `version` question
([questions-spec.md](questions-spec.md)), answered with `weaver answer`. A
version is never invented from the commit hash.

## 3. Edge history per service

`edges.yaml` holds the current map. Earlier maps are kept **per service**, as
snapshots of the edges that service's code defines:

```
knowledge/<domain>/
  edges.yaml                     current effective map
  edges.history/
    checkout/
      1.4.0.yaml
      1.3.0.yaml
    payment/
      2.0.0.yaml
```

**What a service's snapshot holds:** the edges whose code is in that service,
in the `edges.yaml` format (edges-spec §2–3), with the effective `call`:

- Edges with `from: <service>`, together with their `callers`.
- Edges with `to: <service>` from an infrastructure node (consume or
  subscribe), together with their `handler`.
- The nodes those edges refer to.

An edge between two services is stored with its caller, under `from`.

**Rules:**

- **When a snapshot is written:** only when a build of a new release changes
  that service's edges, compared with its newest snapshot. "Changed" means
  `from`, `to`, `kind`, `resource`, `op` or `call` differ, or the set of
  edges differs. Moved line numbers or new `called_by`/`entries` don't count
  as a change.
- **How a snapshot is named:** after the release it was first built from, so
  a snapshot file name is always a `releases[].version`.
- **Linking releases to snapshots:** every release points at the snapshot
  that describes it through `releases[].edges` in `releases.yaml`.
- **Retention:** every snapshot is kept, like every release.
- **Releases without a version:** a release with no resolved version (§2.1)
  gets a snapshot named after its short `commitHash` until the version is
  known.

**Use:** to see what changed in a service's dependencies between two releases,
diff the snapshots their `edges` point at; the same snapshot means no change.

## 4. Versions in Zoekt and kb.db

| Store              | Versions kept                                              | Why                                                                                                                                                            |
| ------------------ | ---------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Zoekt (`zoekt/`) | Every release in `releases.yaml` | So falcon can read the code of the deployed release, including after a rollback: the latest commit built for that version (§2) |
| kb.db              | Every release, as for Zoekt | So `definition`, `references` and `call_chain` work on the code of any release |

**Zoekt.**

- Each release is indexed as one Zoekt **branch** of the service's
  repository, named after the release's `version`, with its `commitHash` as
  the branch version. The newest release is also indexed as the service's
  `branch` from `sources.yaml`, so queries that don't name a release search
  current code.
- Releases are indexed from git objects, not from the checkout, so old
  releases don't need a checkout on disk.
- Zoekt stores each file content once, plus a mask of the branches it
  appears on, so many releases cost little more than one when most files
  don't change.
- Every release gets its branch, whether or not its edges changed: code
  retention doesn't follow the edge snapshots.

Falcon picks a release with a branch filter:

    repo:^checkout$ branch:1.3.2 placeOrder

The branch name is the release's `version`. `commitHash` is only metadata on
the branch, so the branch name stays readable.

**kb.db.**

- **Stored by document, as Zoekt stores files.** SCIP rows (`occurrences`,
  `symbols`) belong to a **document**: one file's SCIP data, keyed by a hash
  of its path, its content and its resolved symbols. A release is the list of
  documents it contains, under its `version` (as for Zoekt branches).
- **Unchanged files cost nothing.** A file that didn't change shares its
  document with the releases before it. One whose symbols changed gets a new
  document even with the same text: a dependency bump turns
  `spring-data-redis 3.5.11` into `3.5.12` in every symbol it resolves.
- A build indexes only the current release of each service and adds the
  documents that are new. An old release is never indexed again.
- The document store and Zoekt's shards are shared by every generation
  (weaver-architecture §2): a build adds to them and never copies them.
- A monorepo's shared files are stored once, whichever service's releases
  list them.
- Size grows with what changes, not with the number of releases: a repo costs
  its first release plus the documents later releases changed. For 20 repos
  of about 800 files, 100 releases each, with a tenth of the files changing
  per release, kb.db and Zoekt together take about 9 GB.
- Zoekt and kb.db always hold the same releases: all of them.
- Queries default to the current release; a tool call names another with
  `release`.

## 5. Internal libraries

Internal libraries are declared in `sources.yaml` next to the services:

```yaml
services:
  - {serviceName: checkout, gitUrl: https://git.acme.com/shop/checkout, branch: release}
libraries:
  - name: acme-kafka
    gitUrl: https://git.acme.com/platform/acme-kafka
    package: maven/com.acme/acme-kafka        # as it appears in SCIP symbols
    tag: "v{version}"                          # git tag of a released version
```

| Field | Meaning |
|---|---|
| `name` | Library id, used in `lib: <name>@<version>` |
| `package` | The package part of its SCIP symbols: Maven `maven/<groupId>/<artifactId>`, or a Go module path. One library may list several |
| `tag` | How a version maps to a git tag. `{version}` is replaced, e.g. `v{version}` or `acme-kafka-{version}` |

**Rules:**
1. **Which versions to index.** After the services are indexed, weaver reads
   the versions of internal packages that each service references. It takes
   them from the service's own SCIP index, i.e. the version the build
   actually resolved. It doesn't parse `pom.xml` or `go.mod`.
2. **Clone once per version, index once.** Each `<library>@<version>` is
   cloned at its tag into `sources/<domain>/.libs/<name>@<version>/`, then
   SCIP-indexed and cached like a service. Several services on the same
   version share one index. A library version is kept as long as any release
   in `releases.yaml` references it, so `definition` and `call_chain` into
   library code work on old releases too.
3. **What a library contributes.** Library code yields wrapper methods,
   constants and the code a `call_chain` walks through, and its code text
   goes into Zoekt as repo `<name>@<version>`. Libraries are not nodes and
   produce no edges of their own: their calls count where a service calls
   them.
4. **Unknown internal packages.** Weaver asks once (questions-spec) about a referenced
   package that looks internal (it shares a prefix with a declared service or
   library package) but isn't declared: `com.acme/acme-redis 2.1.0: gitUrl? tag?`.
   Until it's answered, matching for that package falls back to the external
   rule.
5. **Versions without a tag.** Snapshot or unresolved versions (`1.0-SNAPSHOT`,
   `${revision}`) have no released tag. Weaver indexes the library's
   `branch` (an optional field, default `main`) in their place, marks those
   references `lib: <name>@<branch>`, and lists them in the review queue.
   A version is never invented.
